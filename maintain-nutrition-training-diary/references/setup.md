# Настройка дневника под пользователя

Разделять переносимый навык и личные данные. Навык содержит общие процедуры; профиль, подключения, журналы и медицинская история находятся вне его папки. Не поставлять чужой заполненный профиль как начальные значения. Все примеры и проверочные случаи — синтетические.

Первый запуск не повторять для каждой еды или вопроса. Если профиль и схема уже загружены в доступный контекст и нет признаков изменения, использовать их. При утрате контекста восстановить только нужную часть; источник и версия не угадываются.

## Новый дневник по умолчанию: Google Sheets

Если пользователь поручил создать новый дневник и не выбрал иное, использовать нативную Google-таблицу на Google Диске и [эталонные листы/колонки](default-schema.md). Формат — `google_sheets`, хранилище — `google_drive`. Существующий профиль, конкретный выбранный файл, иной формат или более узкий состав модулей имеют приоритет.

1. Через Google Drive установить точный выбранный файл/папку и доступ. Для нативного источника подтвердить MIME `application/vnd.google-apps.spreadsheet`. При создании нового дневника использовать штатный workflow Google Sheets; неизвестные ID не придумывать. Действующий файл не копировать и не переносить из-за смены значения по умолчанию.
2. При первичном подключении получить метаданные, названия листов, sheetId и нужные заголовки; сохранить сопоставление во внешний профиль и рабочий контекст. Для нового полного дневника использовать девять базовых листов и журналы выбранных активностей, без чужих данных. Существующую структуру сохранить.
3. Обычные чтения выполнять через Google Sheets по ограниченным нужным диапазонам, например get_spreadsheet_range/get_spreadsheet_cells; записи — соответствующими диапазонными операциями/batch_update_spreadsheet. Повторно использовать известные ID и карту. Не скачивать XLSX, не читать его локальную версию и не запускать pandas для обычной записи еды или вопроса к таблице.
4. При изменении существующей строки учитывать её текущие данные, формулы, валидацию и формат. Зависимые правки объединять в один атомарный batch. Для новых событий использовать поддерживаемое добавление без перезаписи чужой строки. Атомарность пакета не означает наличия файлового CAS; при возможном конфликте сверять целевые ячейки, а не полагаться на номер версии локального файла. После успеха обновлять контекст и итог.
5. XLSX — резервный экспорт этой же таблицы по необходимости или отдельному поручению. Снимок может устареть: отмечать дату и полноту. Он не второй журнал, не автоматический основной источник и не повод синхронизировать два набора записей. Если API записи недоступен, не заявлять сохранение и не записывать факт только в резервную копию.
6. Профиль содержит фактический ID/URL основного Google-файла, папку, владельца, карту листов и доступные способы чтения/записи. Секреты подключения в навык не включать. Смена основного источника — явное решение пользователя, после проверки данных и доступности нового источника.

## Блокировка записи

- Использовать общую для всех агентов эксклюзивную блокировку по устойчивому ID дневника. Получать её после подготовки данных, перед чтением целевых строк для проверки дублей и конфликтов. Под блокировкой перечитать цель, выполнить запись, проверить результат и освободить её. При занятой блокировке ждать ограниченное время или сообщить, что запись отложена. Не держать её во время долгого расчёта или ожидания ответа пользователя. Дополнительно применять условное сохранение по версии, если оно доступно.
- В Google Sheets использовать общий для этой книги положительный `metadataId` (значение протокола по умолчанию `2097846317`), ключ `diary.write-lock.v1` и новый случайный токен каждой попытки. При подтверждённой коллизии с посторонними метаданными согласовать другой ID и закрепить его во внешнем профиле для всех агентов. Не менять ID в ответ на занятость своей блокировки. Запрос захвата через `batch_update_spreadsheet`: `{"createDeveloperMetadata":{"developerMetadata":{"metadataId":2097846317,"metadataKey":"diary.write-lock.v1","metadataValue":"<уникальный токен>","location":{"spreadsheet":true},"visibility":"DOCUMENT"}}}`. Google отклоняет создание, если ID занят. После подтверждения захвата перечитать цели и отправить точечный пакет. Протокол координирует соблюдающих его агентов. Ручные редакторы и другие клиенты могут менять таблицу, поэтому беречь соседние ячейки и сверять целевую запись.
- Освобождать блокировку отдельным `deleteDeveloperMetadata` с `dataFilter.developerMetadataLookup`, содержащим одновременно `metadataId`, `metadataKey`, `metadataValue` своего захвата и `visibility: DOCUMENT`. Это фильтр освобождения, поэтому не использовать его как условие записи. При подтверждённом отказе записи или отмене до отправки также освобождать свою блокировку. При неизвестном исходе сверить статус и целевые данные, по возможности по устойчивому ключу исходного сообщения и факта. Одна пустая проверка не исключает позднее применение. Не повторять запись и не снимать блокировку, пока исход не установлен. При неизвестном результате захвата продолжать только после подтверждения своего токена через API метаданных. Истёкшее время само по себе не даёт права снять чужую блокировку. Восстановление возможно после подтверждения, что прежний исполнитель и его запросы завершены.
- В другом хранилище использовать его общую блокировку или проверенную очередь с одним исполнителем записи. Если выбранный маршрут не умеет координировать агентов, подготовить изменение и сообщить, что запись ждёт безопасного способа. Не имитировать блокировку заметкой, проверкой пустой ячейки или локальным файлом в окружении одного агента.

## Явно выбранный Excel или резервное чтение

Если пользователь отдельно выбрал Excel, сохранять Office-формат `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`. XLSX на Drive требует получения исходных байтов и замены того же Drive file ID; Google Sheets range API к нему неприменим. Использовать Spreadsheets и Google Drive, не создавать новый файл на каждое сохранение и не конвертировать источник молча. Если нет условной замены, не обещать атомарную защиту версией из метаданных; перед записью сверять состояние, а при известной параллельной записи согласовать последовательный режим. Для Library и иных хранилищ использовать их штатное сохранение с доступной защитой версии.

## Первый запуск

1. Найти явно указанный профиль в инструкции проекта или выбранном пользователем файле. Если профиля нет, сначала использовать уже сообщённые сведения и доступный выбранный дневник. Спросить один главный вопрос: какой существующий дневник подключить либо нужно создать новый. Не искать чужую таблицу по одному совпадающему названию.
2. Установить владельца данных и основной источник: тип хранилища, точный идентификатор/путь, доступные операции и способ сохранения. Одноимённые файлы, архивы и копии не считать взаимозаменяемыми. Не выбирать XLSX или Google Sheets по умолчанию вопреки указанию пользователя.
3. Для существующего источника прочитать структуру и сопоставить поля с логическими ролями из [схемы](schema.md); сохранить его организацию. Для явно порученного нового дневника использовать [структуру по умолчанию](default-schema.md), если пользователь не выбрал иную. Спортивные журналы добавлять по его видам активности; силовые и фридайвинг не являются обязательным набором. Отключённые модули не создавать ради совпадения с примером.
4. Установить язык ответа, часовой пояс и единицы. Использовать подтверждённые значения; язык можно первоначально взять из сообщения. Не выводить часовой пояс из языка, валюты, устройства или местоположения сервера. При неоднозначной дате задать один вопрос; не придумывать дату события.
5. Найти актуальные цели, предпочтения, ограничения и соглашения учёта в выбранном дневнике. Когда их нет, собирать постепенно по задаче. Для простой записи еды не требовать целей по весу, полного анамнеза или тренировочной анкеты. Для рекомендации уточнить только параметр, который существенно меняет решение.
6. Сохранить профиль вне папки навыка, в согласованном месте проекта. Закрепить устойчивый ID или путь профиля в инструкции проекта или ином доступном новым чатам месте. Если агент не может сохранить указатель, сообщить, какой указатель нужно закрепить. При утрате указателя запросить подтверждённый профиль или выбранный дневник. Секреты хранить в защищённом подключении.
7. Проверить чтение и сохранение при первой реальной записи; не добавлять тестовые события в живой дневник. После сохранения подтвердить, какой источник настроен, что доступно и какие существенные поля пока неизвестны.
8. При первичной настройке спросить отдельно, показывать ли накопленное КБЖУ после каждой записи еды и показывать ли автоматически оценку суточного расхода после записи еды и при запросе КБЖУ. Сохранить два независимых ответа в действующей персонализации. Уже известные ответы не запрашивать повторно. До выбора в новом дневнике показывать КБЖУ порции, а дневные показатели — по запросу. Для действующего дневника сохранить привычный формат до явного изменения. Прямой запрос выполняется независимо от настроек автоматического вывода.
9. При настройке оценки расхода собрать известные исходные данные одним коротким блоком. Спросить рост, текущий вес и дату взвешивания, известный BMR/RMR с единицами, датой и источником, если он есть. Если расход в покое нужно оценить формулой, уточнить возраст и применимую половую константу по данным пользователя. Для шагов уточнить, доступны ли дистанция, длина шага или обычный темп, и можно ли получить шаги и расстояние одной контрольной прогулки. Для часов или телефона уточнить модель, какие метрики доступны (активные/общие ккал) и какие интервалы и тренировки они покрывают. Не блокировать ведение дневника из-за неизвестного ответа. Хранить подтверждённые настройки в персонализации, датированные вес и измеренный обмен — в замерах либо в сопоставленном источнике.

## Состав профиля

Профиль может быть Markdown, YAML, JSON либо существующим разделом настроек системы. Формат не важнее однозначности и доступности. Не требовать все поля для каждого действия.

| Группа | Что задавать |
|---|---|
| Владелец | Имя/псевдоним или идентификатор владельца; правила разграничения при нескольких людях |
| Основной источник | Раздельно `backend` (формат), `storage` (хранилище), `locator` (проверенный ID/путь). Для нового дневника стандарт — google_sheets + google_drive; уже выбранный источник не менять |
| Доступ | Подключение/инструмент, права чтения и записи, контроль версии; без токенов и паролей |
| Локализация | Язык ответа, часовой пояс, единицы веса/длины/энергии; предпочтительная краткость |
| Схема | Реальные листы/таблицы/поля для логических ролей; даты, форматы единиц, поддерживаемые категории |
| Актуальная персонализация | Адрес её единственного действующего источника; цели и сроки, питание, непереносимости, предпочтения, ограничения и расписание читать оттуда |
| Модули | Питание, силовые, другие виды спорта, сон/самочувствие, измерения, препараты/БАДы — по реальным задачам пользователя |
| Учёт | Режим воды/напитков, выбранный режим КБЖУ БАДов (по умолчанию исключены; включение — по явному выбору), обычные порции, точность; сами карточки хранить в дневнике |
| Источники еды | Приоритет этикетки/карточки/оценки; нужны ли URL, какие источники допустимы. Сохранённые корректные данные не требуют постоянной проверки ссылок |
| Сопровождение | Режим быстрой записи и разбора, частота проверки результатов по запросу, допустимые упрощения; уведомления только по отдельному поручению |
| Ограничения данных | Датированные интервалы условных часов, неполное покрытие, ошибки устройства, смена единиц/рецептов; не применять к другим пользователям |
| Личный контекст | Необязательный адрес истории и датированных уточнений вне навыка; факты свежего дневника имеют приоритет |

## Шаблон нового дневника со стандартными настройками

Шаблон: [assets/profile.example.yaml](../assets/profile.example.yaml). Скопировать его в приватное хранилище вне репозитория, затем заполнять только подтверждёнными данными текущего пользователя.

`null` означает неизвестное, а не запрет, ноль или установленную норму. Этот шаблон предназначен для создания нового дневника, а не замены существующего профиля. Состав модулей можно сократить по явному запросу. Пустой `activity_types` означает, что виды тренировок ещё не заданы: не подставлять силовые и фридайвинг автоматически. Неизвестный необязательный параметр не блокирует сохранение доступного факта. Обычные порции, цели, рацион и исключения одного пользователя никогда не заполнять из истории другого.

## Обновление и перенос

- Разовое намерение тренироваться не сохранять в дневник без прямой просьбы; факты сохранять сразу. Настройку КБЖУ БАДов и её изменения вести в единственном источнике актуальной персонализации.
- Новое явное уточнение пользователя применять к нужному событию и, при необходимости, существующей настройке с датой/источником. Не распространять новый рецепт, режим или предпочтение на старые факты.
- При смене источника сначала установить единственный новый основной дневник и проверить права; не синхронизировать два журнала молча. При конфликте выбранного профиля с новым явным указанием уточнить только источник до фактической записи.
- Для передачи другому человеку переносить папку навыка; новый пользователь проходит собственную настройку. Не включать личный профиль, дневник, снимки, медицинские сведения или ключи в распространяемый комплект.
- Обновление навыка не перезаписывает внешний профиль, историю или дневник. Изменение схемы требует согласования; отсутствие привычного листа не повод перестроить чужую книгу.
