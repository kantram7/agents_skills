# Логическая схема дневника

Для нового дневника применять [структуру по умолчанию](default-schema.md): базовые листы и настраиваемые журналы видов активности. Для существующего сопоставлять роли с его листами, таблицами, полями и единицами; шаблон не даёт права перестроить выбранную книгу. Здесь нет обязательного числа листов, букв колонок, имён файлов, дат или текущего количества записей. XLSX, Google Sheets и иные поддерживаемые хранилища используют одинаковый смысл данных; конкретные операции задаёт инструмент подключения.

## Минимум для работы

- Определить владельца и источник; при нескольких людях иметь однозначный owner/person ID либо раздельные дневники.
- Для факта сохранять тип, дату события (или явную неопределённость), описание, количество/единицы, источник и значимые оговорки. Не превращать пустое значение в ноль.
- Использовать существующие ID записей, когда они есть. Если среда предоставляет устойчивый ID исходного сообщения, использовать его вместе с номером факта в сообщении. Сохранять ключ одновременно с фактом в поддерживаемом поле ID или в согласованном поле источника/заметок. При отсутствии ключа искать событие по дате, типу, времени, предмету и контексту. Номер строки может измениться. Две одинаковые порции из разных подтверждённых сообщений могут быть разными событиями.
- В журналах с пустыми строками находить заполненные записи по значениям, не по форматированной границе или первой пустой строке. Проверять также заполненные ячейки вне карты полей и под пустыми заголовками; не игнорировать и не терять их при экспорте.
- Хранить все подтверждённые сведения, которые вмещает существующая схема. Если отсутствует существенное поле, предложить минимальное размещение; не терять факт и не перестраивать чужую таблицу молча.

Силовые и фридайвинг являются видами активности наряду с бегом, велосипедом, йогой и другими занятиями. Роли strength/freediving — специализированные формы sport_sessions, а не универсальные обязательные модули. Лист «Активность» в стандартной книге хранит повседневную и отдельно не выделенную активность; наличие специализированного журнала не разрешает повторно записывать там ту же сессию и её расход.

## Роли и поля

Названия в скобках — возможные примеры, не требуемые имена листов.

| Роль | Сведения |
|---|---|
| Питание (`meals`) | Владелец, дата/время, приём пищи, продукт/рецепт, съеденное количество и единицы, энергия, белки/жиры/углеводы, клетчатка, источник, точность, комментарий |
| Продукты и рецепты (`foods`) | Название/бренд/версия, база расчёта на 100 г/мл либо порцию, состав, масса ингредиентов и готовый выход, порция по умолчанию, использованные данные, дата обновления |
| Посуда (`containers`, необязательно) | Название и приметы, масса пустой тары, объём, дата и источник |
| Силовые (`strength`, необязательно) | Дата/время, фокус, длительность, мышцы, упражнения, рабочие/разминочные подходы, веса с единицами, повторения, отдых, RPE/RIR, техника и симптомы; данные часов при наличии |
| Другие тренировки (`sport_sessions`, необязательно) | Вид, дата, условия, длительность, задача, объём/дистанция/повторы с единицами, отдых, усилие, ощущения и источник |
| Фридайвинг (`freediving`, только при включении) | Среда и дисциплина, бассейн/глубина, ласты/без ласт, положение, результат/объём, задержки и отдых, техника, контракции, продувка, симптомы, страховка/тренер, данные часов |
| Повседневная активность (`activity`, необязательно) | Шаги, прогулки и другие отдельные активности, дата, длительность/дистанция, источник. Не дублировать специализированную сессию |
| Замеры (`measurements`, необязательно) | Показатель, значение и единицы, дата, прибор, условия, источник; показатели анализов сохранять без самостоятельного диагноза |
| Сон и состояние (`wellbeing`, необязательно) | Ночь/дневной сон/бодрствующий отдых раздельно, длительность и формат времени, качество, энергия/стресс/симптомы, шкала только со слов пользователя |
| Справочник препаратов/БАДов (`supplement_catalog`, необязательно) | Продукт, форма, единица, состав, доза вещества на единицу, этикеточный режим, период актуальности, источник |
| Фактический приём (`supplement_intake`, необязательно) | Дата/время, продукт, количество/единица, рассчитанная доза, обстоятельства и источник. План и факт различать |
| История и решения (`history_decisions`, необязательно) | Датированные исторические периоды, достижения и заключения с точностью; решения/гипотезы со статусом и проверкой по coaching.md |
| Персонализация (`personalization`) | Цели и сроки, текущие ориентиры, предпочтения, ограничения, расписание и соглашения учёта; дата/источник и признак действующей версии |

Роли могут делить один лист либо располагаться в нескольких таблицах. Не требовать отдельный лист для каждой. В незнакомой схеме не угадывать смысл колонок по позиции. Не включённый модуль не создавать; когда пользователь сообщает новый вид события, уточнить его размещение по необходимости.

## Смысл и единицы

- Для энергии различать пищевые значения, активные калории и общий расход, ккал и кДж. Не складывать метрики с разным смыслом и не менять единицы без пересчёта.
- Для весов различать кг/фунты, массу одной гантели/общую, добавленный вес/вес тела. Не предполагать ни массу грифа, ни формат чужой записи.
- Для длительности различать десятичные часы, часы:минуты и минуты/секунды. Часовой пояс и трактовку дат брать из профиля.
- Для структурированной оценки сохранять название шкалы; текстовое «хорошо» не превращать в числовой балл.
- Значения на 100 г, порцию и упаковку хранить с явной базой; сырую и готовую массу различать.
- Физические числовые значения хранить числами с явной единицей/базой, а не строками; перед преобразованием учитывать десятичный разделитель. Даты, диапазоны, идентификаторы и описания доз не преобразовывать вслепую.
- План будущей тренировки сохранять только по явной просьбе, отдельно по смыслу от выполненной сессии; пустые строки ожидания отчёта не создавать.
- Необязательные поля оставлять неизвестными. Датированные ограничения старых данных (условные часы, неполное покрытие) задаются только в профиле их владельца.

## Совместимость и изменение схемы

Читать реальные заголовки при подключении, фиксировать сопоставление в профиле вне навыка. При изменении заголовков пересмотреть адреса; не писать по старым буквам колонок. Не хранить правила ведения вторым полным текстом в источнике данных. Существующие согласованные формы отчётов и табы сохранять; новые создавать только по поручению пользователя.
## Полнота КБЖУ

- По каждому показателю отдельно суммировать только известные числа по относящимся к нему строкам, включая явные нули. Если ни одного числа нет, выводить «нет данных». Если часть строк без значения, писать «известно ≥…» для неотрицательных показателей или «по известным позициям …» и указывать покрытие, например «белок 25 г по 2 из 3 позиций». Оценочные компоненты маркировать как приблизительные, без знака строгой нижней границы. Исключённые по правилам БАДы не входят в знаменатель.
- Различать полноту нутриента по внесённым строкам и полноту журнала дня. Даже при заполнении всех полей итог остаётся «по записям», пока покрытие дня не подтверждено. Текущий день показывать накопленно, если он ещё не закрыт.
- При явном подтверждении полноты питания сохранить датированный статус и его источник в сопоставленном поле. Для нового шаблона использовать один комментарий в существующей строке питания за эту дату, например `Покрытие питания 2026-01-15 — подтверждено владельцем`. Если строки нет, использовать согласованное существующее поле статуса дня, без вымышленной порции. Если подтверждение отозвано, обновить маркер на месте. При отсутствии сохранённого статуса и доступного подтверждения не считать прошедший день полным по умолчанию.
- В среднем по суткам для каждого показателя использовать только сопоставимые дни с подтверждённым покрытием дня и без неизвестных значений этого показателя. Указывать число таких дней из запрошенного периода. Если их нет, дать известные подытоги с покрытием. Среднее по частичным дням допустимо отдельно по запросу как среднее по записанному, с явным знаменателем.

## КБЖУ БАДов и исправление дозы

- Хранить датированные включения и отмены в персонализации с областью, моментом начала и источником. Для нового факта, включая поздно сообщённый, выбирать правило на дату приёма. В пересечении областей использовать более узкое правило (продукт → группа → все), внутри одинаковой области — наиболее позднее из действовавших. Если пользователь явно заменил все предыдущие правила, закрыть их с указанной даты. При равном приоритете и противоречии уточнить настройку. «С сегодняшнего дня» относится к дате события, «с этой дозы» — начиная с указанного приёма. Уже внесённые приёмы пересчитывать только по отдельному поручению.
- Присваивать приёму устойчивый ID, используя имеющийся ID или отдельный ключ события. Сохранять этот ключ и ссылку на применённое правило в строке приёма и связанной строке питания, если она есть. В схеме без полей ID использовать согласованное поле источника/комментария. Физический номер строки сам по себе недостаточен.
- При исправлении найти исходную дозу и её единственный пищевой вклад по ключу, затем исправить обе записи на месте в одном атомарном пакете под блокировкой. При историческом исключении исправлять только дозу. Для старой записи без ключа сопоставить дату, время, продукт, дозу и источник, а при неоднозначности уточнить связь до правки. Если атомарности нет, удерживать общую блокировку, проверять каждую часть по тому же ключу и при сбое доводить до согласованности только недостающую часть. Пока согласованность не подтверждена, явно сообщать статус и отмечать затронутый итог как непроверенный.
